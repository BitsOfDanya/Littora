# Littora

Littora — рабочее пространство для спутникового мониторинга макропластика в морских акваториях. Проект команды «5 bit» для финала КосмоХакатона, кейс «Детектирование и оценка концентрации макропластика в морских акваториях».

По снимкам Sentinel-2 система будет:

- находить вероятные скопления плавающего мусора;
- оценивать степень загрязнения;
- показывать, как пятна меняются от снимка к снимку и куда их сносит течение;
- подсказывать, какие участки стоит обследовать с судна или беспилотника.

## Статус

Сервис работает на реальных данных; модели детекции и концентрации пока не подключены, и интерфейс это прямо показывает.

- **Данные кейса.** CSV организаторов разобран: отбор записей под целевую величину, проверка C = N/A, реестр пар «наблюдение — снимок Sentinel-2» с причиной для каждого решения.
- **Анализ района.** Запрос по участку и дате: сервер находит снимок Sentinel-2 L2A, строит RGB и маску качества по слою SCL, оценивает пригодность и выдаёт один из официальных статусов. Результат сохраняется, повтор запроса возвращает тот же ответ.
- **Интерфейс.** Экран входа и рабочее пространство на одной карте, пять режимов. В «Мониторинге» — снимки района на шкале времени, снимок даты и маска качества на карте, полевые измерения в шт./км², панель анализа с выгрузкой GeoJSON и CSV и историей запросов с фильтрами по дате и статусу.
- **Запуск.** Docker Compose поднимает всё целиком.

Демонстрационный сценарий сохранён: клавиша `D` включает фикстуры на эталонном участке «Гондурасский залив», они помечены «ДЕМО». По умолчанию демо выключено.

Пока не реализовано:

- детектор и модель концентрации — место под них готово (`Detector`, `ConcentrationModel` в `backend/app/analysis/models.py`);
- спектральные композиты и индексы (FDI, NDVI) — пока только RGB;
- расчёт дрейфа и ранжирование участков для обследования.

## Исследование данных (EDA)

Метрики рассчитаны отдельно для каждого профиля. Это исследовательская проверка

Команды и окружение: [ml/eda/README.md](ml/eda/README.md).

Проверены все 1381 изображения и маски, подготовлено разбиение с учётом соседних

## Целевая величина

Задана в `backend/config/case.toml`, единица — шт./км², C = N / A.

| Ключ | Что считаем | Профили | Событий |
|---|---|---|---|
| `litter-visual`, основная | плавающий мусор ≥ 2–2,5 см, визуальный учёт с судна | `S3_visual_GT2`, `S4_visual_GT2_5` | 74 |
| `plastic-visual` | суммарный пластик ≥ 2 см, визуальный учёт | `S2_visual_GT2` | 63 |
| `plastic-trawl` | макропластик 5–50 см, поверхностный трал | `S1_trawl_5_to_50` | 83 |

Профили с разными размерными классами и методами не смешиваются. Метрики по основной величине считаются отдельно по каждому профилю.

Отбор записей:

- в цель идут только `transect_density` с концентрацией, профилем и охватом цели;
- категорийные строки (362) и отдельные предметы (337) — не цель, но остаются в реестре с причиной;
- проверка C = N/A: 461 совпадение, 6 в пределах округления, 116 записей только с опубликованным значением, 15 без значения, расхождений нет;
- поля с ответом (концентрации, счётчики, `reported_*`, `parent_*`) в признаки не попадают.

Пары со снимками:

- Sentinel-2 L2A из Earth Search, коллекция `sentinel-2-c1-l2a`; окно ±3 сут, сдвиг по времени не больше 12 ч, облачность тайла до 40 %;
- по полосе учёта проверяются покрытие, пропуски, облака и тени, доля воды и «яркая вода» по SCL и NIR;
- приняты 9 событий: Чёрное море, рейс DOORS, июнь 2024 — T1, T2, T18–T21, T30–T32; у остальных своя причина: до запуска Sentinel-2, сдвиг по времени, облака, частичное покрытие.

Реестр лежит в `reports/registry/` и в git:

```
observations.csv   все 935 записей: решение, причина, проверка N/A
pairs.csv          207 пар событие — снимок: сдвиг, качество, решение
events.geojson     полосы учёта с лучшей парой
summary.json       сводка и правила подбора
```

Пересобрать:

```bash
cd backend && .venv/bin/python -m app.case select
```

```bash
cd backend && .venv/bin/python -m app.case pair
```

`select` работает без сети, `pair` обращается к каталогу снимков.

## Статусы результата

| Статус | Когда |
|---|---|
| обнаружено | модель нашла зоны мусора на пригодном снимке |
| не обнаружено | снимок пригоден, зон нет |
| недостаточно данных | нет снимка, снимок непригоден или детектор не подключён |
| исследовательская оценка | значение есть, но перенос на снимки не подтверждён |
| концентрация недоступна | значение шт./км² по снимку не выдаётся |

Измерения с судна и оценки модели не смешиваются: в ответах у них разный `value_kind` (`measurement`, `model_estimate`), на карте разные знаки.

## API

Документация — `/api/docs`.

| Метод | Путь | Что отдаёт |
|---|---|---|
| GET | `/api/v1/health`, `/api/v1/meta` | состояние и реестр возможностей |
| GET | `/api/v1/case/targets`, `/api/v1/case/summary` | целевые величины и сводка реестра |
| GET | `/api/v1/observations` | полевые измерения, GeoJSON; фильтры `target`, `decision`, `source`, `date_from`, `date_to`, `bbox` |
| GET | `/api/v1/pairs`, `/api/v1/events` | реестр пар и события с решениями |
| GET | `/api/v1/scenes` | снимки Sentinel-2 L2A по району и периоду, лучший тайл на пролёт |
| POST | `/api/v1/analyses` | анализ района: `bbox`, `date`, `window_days`, `scene_id`, `target` |
| GET | `/api/v1/analyses` | сохранённые запросы; фильтры `status`, `aoi_id`, `date_from`, `date_to` |
| GET | `/api/v1/analyses/{id}` | результат; `image.png`, `mask.png`, `export.geojson`, `export.csv` |

Идентификатор анализа — хеш запроса, выбранной сцены, цели и версии конвейера. Результаты лежат в `data/processed/analyses/<id>/`.

## Архитектура

```
frontend/     Next.js 16, TypeScript, Tailwind CSS 4, MapLibre GL 6, deck.gl 9
backend/      FastAPI, rasterio, shapely, pytest, ruff
ml/           модели, пока пусто
data/         данные; в git каталог источников, районы, манифесты и CSV кейса
reports/      реестр пар и отчёты
scripts/data/ загрузка и подготовка внешних данных
compose.yaml  frontend и backend в контейнерах
```

Frontend:

- Карта одна на всё приложение. Её не пересоздают ни при смене режима, ни при входе с экрана входа.
- Режимы — это страницы Next.js. Каждая добавляет свои панели в общую оболочку и свои слои deck.gl на карту.
- Интерфейс получает данные только через хуки `src/data/*`. Каждый ответ помечен источником: `api`, `demo` или `none`.
- Демонстрационные данные лежат отдельно в `src/demo`. Импортировать их откуда-то ещё запрещает eslint.

Backend:

- `app/case` — данные кейса: конфигурация цели, отбор записей, проверка N/A, геометрия полос, подбор пар, реестр.
- `app/earth` — каталог STAC и чтение COG: доли классов SCL, RGB и маска качества в PNG.
- `app/analysis` — запрос анализа, статусы, сохранение и выгрузка.
- Приложение собирается в `create_app()`.
- Настройки читаются из переменных `LITTORA_*`.
- Ошибки возвращаются в одном формате `{"error": {...}}` с `X-Request-ID`.
- Реестр возможностей платформы отдаётся в `/api/v1/meta`. Когда возможность готова, её статус меняется с `planned` на `available`, и интерфейс сам перестаёт показывать «не подключено».

## Запуск в Docker

Нужен Docker с Compose v2.

```bash
docker compose up -d --build
```

- http://localhost:3000 — приложение;
- http://localhost:8000/api/docs — документация API.

В контейнере фронтенд проксирует `/api/*` в сервис `backend`, поэтому CORS настраивать не нужно. Backend читает `data/case` и `reports` только на чтение, результаты анализов хранит в томе `analyses`. Для снимков нужен доступ в интернет. Порты меняются в `.env` через `LITTORA_FRONTEND_PORT` и `LITTORA_BACKEND_PORT`. После изменения `NEXT_PUBLIC_*` нужна пересборка с `--build`.

```bash
docker compose ps
```

```bash
docker compose down
```

## Продакшен и автодеплой

Push в `main` запускает [GitHub Actions](.github/workflows/deploy.yml): workflow проверяет backend и frontend, затем передаёт архив коммита на сервер и вызывает [deploy/deploy.sh](deploy/deploy.sh). Скрипт под блокировкой собирает образы, обновляет Compose, ждёт healthcheck обоих сервисов и проверяет главную страницу и `/api/v1/health`. При ошибке workflow завершается с ошибкой; номер успешно развернутого коммита записывается в `/opt/littora/deployed-revision`. Ручной запуск доступен через `workflow_dispatch`.

На сервере приложение доступно по `http://5.129.225.86/`. Backend слушает только `127.0.0.1:8000`. Настройки хранятся в `/opt/littora/shared/.env`, результаты анализов — в Docker volume `littora_analyses`. Для SSH деплоя используется отдельный пользователь `littora-deploy` и секрет GitHub Actions `LITTORA_DEPLOY_SSH_KEY_V2`.

```bash
ssh root@5.129.225.86 'cat /opt/littora/deployed-revision; cd /opt/littora/current && docker compose ps'
```

По морям России:

- В `data/aoi/russia.geojson` — 33 района во всех российских морях: порты, устья рек, проливы. По каждому уже найдены чистые летние сцены Sentinel-2.

- Для Copernicus Data Space в форме регистрации нет России. Снимки берутся из Earth Search: там регистрация не нужна.

## Следующие шаги

1. Т2, детектор: сегментация мусора на снимках пар (Residual Attention U-Net), базовая модель по индексам FDI и NDVI для сравнения; P, R, F1 и IoU, сохранённые предсказания. Детектор подключается через `Detector` и сразу меняет статусы анализа.
2. Т3, концентрация: оценка шт./км² по признакам снимка в полосе учёта, MAE и дополнительная метрика против базовой модели. Подключается через `ConcentrationModel`; пока перенос не подтверждён, статус — «исследовательская оценка».
3. Т4, воспроизводимость: разбиение по событиям, фиксированные версии данных и моделей, отчёты в `reports/`.
4. Спектральные композиты и индексы в анализе района, затем дрейф: OpenDrift с течениями Copernicus Marine и ветром.
